- **Names.** A box's name is `rlvr-box-<reservation id>`. Its launch template has that name, its schedules start
  with it, and its S3 prefixes end in it.
- **Launch templates.** The default version of each is the self-running one: capacity-block market type, the
  reservation as target, the block's fixed network interface (so the fixed address: 174.129.98.131 in us-east-1f,
  100.29.118.132 in us-east-1d), a 2,000 GB gp3 disk, instance profile `rlvr-box`, and user data that fetches
  `s3://rlvr-speedrun-<account id>/box/<name>/in/code.tgz` at first boot. Version 2 of the 11-28 template is the
  older hand-run one and is not the default. Templates are tagged `rlvr-box=true`.
- **Launch schedules.** 33 one-time EventBridge Scheduler schedules in the default group, 11 per block, all
  `ENABLED`: `<name>-m0001`, `-m0005`, `-m0010`, `-m0025`, `-m0060`, `-m0180`, `-m0360`, `-m0540`, `-m0720`,
  `-m0900`, `-m1080`. The number is minutes after the block's start, so each block is tried at 11:31, 11:35,
  11:40, 11:55, 12:30, 14:30, 17:30, 20:30, 23:30, 02:30 and 05:30 UTC. Each calls `ec2:runInstances` with the
  template's name (so its default version at that moment), one instance, under role `rlvr-scheduler`, with up
  to 3 retries inside 10 minutes.
- **Role `rlvr-scheduler`** (the role whose 11-05 launches were refused). Inline policy `run-rlvr-box`:
  RunInstances on launch templates tagged `rlvr-box=true` and on the instance, subnet, security group, network
  interface, volume, key pair, capacity reservation, image and snapshot the launch touches; tagging at launch;
  passing role `rlvr-box` to EC2. The 11-05 policy lacked the subnet, security group and network interface.
  Its trust policy names the scheduler service and IAM user `rlvr-agent` (the second is what lets a dry run be
  made under the role).
- **Role and instance profile `rlvr-box`** (what the box runs as). Inline policy `box-s3`: list and read `box/`
  and `box-state/` in the bucket; write only `box/*/out/*` and `box-state/*`; delete only under `box-state/`. The
  box holds no other AWS credentials and none of mine.
- **Bucket rules.** `rlvr-box-state`: objects under `box-state/` expire after 7 days. `rlvr-box-files`: objects
  under `box/` expire after 90 days. Both abort unfinished multipart uploads after 2 days.
- **Bucket layout.**

  | prefix | written by | holds |
  |---|---|---|
  | `box/<name>/in/` | `box_s3.sh stage` on Engaging | `code.tgz` (the code at one commit), `commit`, `plan`, `queue/<q>.txt`, `home.txt` |
  | `box/home/` | `box_s3.sh home` on Engaging | the files under `~` that runs read, shared by all boxes |
  | `box/<name>/out/` | the box | results, the queue snapshot, logs, `status.txt` |
  | `box-state/<name>/` | the box | the saved state of each unfinished seed |

## What a box does by itself

1. **Launch.** The first schedule fires one minute into the block. While an instance holds the block's network
   interface every further launch from the template is refused (`InvalidNetworkInterface.InUse` in the 11-18
   test), whoever makes it. So a launch by hand cannot clash with the schedules: one of the two is refused. If
   the instance dies, the next schedule starts a new one.
2. **First boot (user data, `scripts/aws/box_userdata.sh`).** Creates user `zjason` with Engaging's home layout
   and the agent's and the laptop's ssh keys, writes the block's end to `/etc/rlvr-box.end`, tries to fetch
   `code.tgz` up to 9 times 20 s apart, unpacks it and starts `scripts/aws/box_boot.sh`. Then it builds the venv
   from the pinned package list carried in the user data.
3. **Fetch (`box_boot.sh`).** The plan (retried until it arrives), the queues, `home.txt`, then every path in
   `home.txt` from `box/home/`: starting checkpoints, the tokenizer, and as one tar file each the base model's
   cache and a pretraining token file. Each copy gets 5 tries. A path whose copy or unpacking failed is written
   as `NOT FETCHED: <path>` to the box's log and status file. The workers start all the same; an item that needs
   a missing path fails by itself.
4. **Restore.** If an earlier instance of this box left a queue snapshot in `out/`, the new instance brings the
   results back, rebuilds the queues without the finished items, and brings back each unfinished seed's saved
   state from `box-state/<name>/`.
5. **Work.** When the venv is ready it starts the workers of the plan: one `scripts/aws/box_workers.sh` call per
   plan line (`QUEUE=... GPUS="0 1" PER_GPU=2 ...`). They are the Engaging queue workers, each pinned to a GPU.
   A worker takes no new item when fewer than `RESERVE_MIN` minutes remain before the block's end minus 35 min.
6. **Results leave the box.** Every 5 min: the files of finished and running seeds (no weights), the worker
   logs, a queue snapshot, the box's own logs and `out/status.txt`. Every 60 min, and every 10 min in the last
   75 min of the block: the saved state of each unfinished seed that changed.
7. **Repairs.** A failed item with saved state is run again in place (up to 3 times without progress). Every
   10 min a keeper puts each failed item back in its queue once and restarts a dead worker that has work, up to
   6 times per worker. A reboot starts `box_boot.sh` again through a crontab `@reboot` line.
8. **End.** AWS terminates the instance at the block's end. A real box does not shut itself down when idle, so
   work can be added by hand.

**Which runs keep saved state.** A screen that starts from a checkpoint (track A, and track D's RL-only items)
saves its state every 60 min and resumes from it on a new instance. A track D screen with its own pretraining
saves none: after a lost instance it starts again from the beginning, and only its logs so far are in S3.

## How to check each piece

Read-only, from a checkout with AWS credentials. `<cr>` is a reservation id, `<name>` is `rlvr-box-<cr>`.

| piece | command | what to see |
|---|---|---|
| reservation, template, schedules, instances, recent launches | `bash scripts/aws/box_auto.sh show <cr>` | state `scheduled` (later `active`); the default version says "self-running" and "user data: self-running stage ..."; 11 schedules `ENABLED`; `HOURS=n` sets how far back the RunInstances calls from CloudTrail go |
| the scheduler role may launch | `bash scripts/aws/box_auto.sh dryrun <cr>` | "dry run ok: the rlvr-scheduler role may launch `<name>`". It assumes the role, so it runs as `rlvr-agent` |
| the stage | `bash scripts/aws/box_s3.sh check <name>` | "check ok", the commit, the number of items and paths, and the workers per GPU for the memory check |
| a running box | `bash scripts/aws/box_s3.sh status <name>` | the box's last `status.txt` and its age: markers, any `NOT FETCHED`, GPU memory, live workers, queue lengths, ok and FAILED counts |
| results | `bash scripts/aws/box_s3.sh pull <name> <tag>` | results into the checkout, laid out like `scripts/aws/box_sync.sh from` |

The same without the scripts:

```
aws ec2 describe-capacity-reservations --capacity-reservation-ids <cr> \
  --query 'CapacityReservations[].[State,InstanceType,AvailabilityZone,StartDate,EndDate]'
aws ec2 describe-launch-template-versions --launch-template-name <name> --versions '$Default' \
  --query 'LaunchTemplateVersions[].[VersionNumber,VersionDescription,LaunchTemplateData.InstanceType]'
aws scheduler list-schedules --name-prefix <name>-m --query 'Schedules[].[Name,State]'
aws scheduler get-schedule --name <name>-m0001 --query '[ScheduleExpression,Target.RoleArn,Target.Input]'
aws iam get-role-policy --role-name rlvr-scheduler --policy-name run-rlvr-box
aws iam get-role-policy --role-name rlvr-box --policy-name box-s3
aws s3api get-bucket-lifecycle-configuration --bucket rlvr-speedrun-<account id>
aws s3 ls s3://rlvr-speedrun-<account id>/box/<name>/in/ --recursive
aws s3 cp s3://rlvr-speedrun-<account id>/box/<name>/out/status.txt -
```

On a box (ssh as `zjason`): `~/box_boot.log`, `/var/log/rlvr-box.log` (user data), `~/.box_boot/` (markers
`fetched`, `fetch_failed`, `restored`, `workers_started`; `status.txt`; `keeper.log`), `queue/worker.log`.
Copies of both logs are in `box/<name>/out/log/<instance id>/`.

## Rules for running it by hand

- **Stage before the launch.** `box_s3.sh stage`, then `home` (as a `mit_normal` CPU job), then `check`, with
  the same `HOME_EXTRA` for all three. A box that finds no `code.tgz` in its first three minutes does not start
  by itself.
- **Before terminating a box on purpose inside its block, run `box_auto.sh unschedule <cr>`.** Otherwise the
  next schedule launches a new instance.
- **Do not run `scripts/aws/box_launch.sh` for these reservations.** It deletes the template and makes one
  without the self-running stage. If that happened, run `box_auto.sh template <cr>` again; the schedules name
  the template, not a version.
- **To change what a box runs after it started**, ssh in and edit its queues as on the 11-18 box. Staging again
  changes only what a new instance fetches. `touch queue/keeper.off` on the box stops the keeper.
- **Before a re-test** on the cheap instance: `box_auto.sh template test` (the test template's block end is 3 h
  after it is made), `box_auto.sh dryrun test`, and `box_s3.sh clear rlvr-box-test` (otherwise the new instance
  restores the last test's finished snapshot and shuts down).

**Not tested.** Anything on a GPU instance: the capacity-block launch itself (dry-run only), the venv build
started from this user data, a real checkpoint directory, the base model's cache and the 4.64 GB token file
through `box/home/`, and a real run's saved state through S3. The first real boot is on the 11-25 block. If it
does not start work by itself, the box is still reachable by ssh and is run as on 11-18.

**Known limits.** A fetched file that is complete but wrong is not caught on the box; `check` looks at the stage
from Engaging before a launch. A screen that starts from a checkpoint made by another item on the same box is
not supported (`check` reports its checkpoint as missing). Pretraining screens keep no saved state (see above).
